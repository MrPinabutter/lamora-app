# Arquitetura

O projeto segue uma organização **feature-first**: código que muda junto fica
junto.

## Quatro princípios inegociáveis

1. **Feature-first, não tipo-first.** Cada feature (`products`, `cart`, `auth`)
   contém seus próprios componentes, hooks, stores, serviços e tipos. Pastas
   globais existem só para o que é genuinamente compartilhado.
2. **Server Components por padrão.** Todo componente é Server Component até
   precisar de interatividade. `"use client"` é uma exceção consciente,
   colocada o mais fundo possível na árvore (nas folhas).
3. **Dependências unidirecionais.** O fluxo é sempre
   `app/ → features/ → shared/`. Uma feature nunca importa outra feature
   diretamente.
4. **Lógica fora do JSX.** Componentes renderizam. Hooks orquestram. Serviços
   buscam e transformam dados. Stores guardam estado de UI.

## Estrutura de pastas

```
src/
├── app/        Roteamento e composição. Sem regra de negócio.
├── features/   O coração do app. Uma pasta por domínio.
├── shared/     Genérico, compartilhado entre 2+ features.
├── store/      Combinação dos slices Zustand.
└── server/     Infra de servidor, nunca importada no client.
```

Cada feature expõe sua API pública por um barrel `index.ts` — só o que está
exportado ali pode ser importado de fora.

Essas regras **não são apenas convenção**: o `eslint-plugin-boundaries` as
aplica no lint. Um import que cruza uma fronteira proibida quebra o build.

## Acesso a dados

Toda leitura e escrita passa por uma **service layer** (`features/*/services/`).
Componentes e Server Actions chamam serviços — nunca o Prisma diretamente. O
import de `@prisma/client` fora de `server/` é bloqueado pelo ESLint.

Arquivos sensíveis ao servidor levam a diretiva `import "server-only"` para
garantir que nunca acabem em um bundle de cliente.

## Mutações

Mutações (cadastro, CRUD, exclusão de conta) usam **Server Actions**. A
validação acontece com um schema **Zod único**, compartilhado entre o
formulário (cliente) e a action (servidor) — nunca confie só no cliente.
